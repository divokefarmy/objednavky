# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Static web app for **Divoké Farmy** — a Czech-language order form + admin/warehouse panel + delivery-note (dodací list) system for meat products. Three source files: `index.html` (structure), `css/styles.css` (all styles), `js/app.js` (all logic, vanilla JS). No build system, no `package.json`, no bundler.

Remote: `github.com/divokefarmy/objednavky`. UI text is Czech — preserve the language when editing.

## Run / develop / deploy

- **Local dev**: `cp js/config.example.js js/config.js`, fill in values, then serve the directory (`python3 -m http.server`). `js/config.js` is gitignored.
- **Deploy**: pushing to `main` triggers `.github/workflows/deploy.yml`, which generates `js/config.js` from repository secrets and publishes to GitHub Pages. Required secrets: `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `EMAILJS_PUBLIC_KEY`, `EMAILJS_SERVICE_ID`, `EMAILJS_TEMPLATE_ID`, `ADMIN_PW`. Optional repo variable: `EMAIL_TO`.
- No test suite, linter, or formatter. Don't invent commands that aren't there.

## External dependencies (loaded via CDN in `<head>`)

- `@supabase/supabase-js@2` — backend (Postgres + Auth)
- `@emailjs/browser@4` — order/DL email notifications from the browser
- `jspdf` + `jspdf-autotable` — client-side PDF generation for orders and delivery notes

All four are required at runtime. If you change one, change it in `index.html`.

## Configuration / secrets

Runtime config is read from `window.DF_CONFIG` at the top of `js/app.js`. The object is provided by `js/config.js`, which is **never committed** — it's generated by the deploy workflow from GH secrets, or copied from `js/config.example.js` for local dev.

Keys: `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `EMAILJS_PUBLIC_KEY`, `EMAILJS_SERVICE_ID`, `EMAILJS_TEMPLATE_ID`, `ADMIN_PW`, `EMAIL_TO`. `VAT` (=0.12) stays hardcoded in `app.js`.

Note: `SUPABASE_ANON_KEY` and `EMAILJS_PUBLIC_KEY` are **public-by-design** (browser code) — security relies on Supabase RLS and EmailJS template-side auth. Never put server-role / private keys in `DF_CONFIG`. `ADMIN_PW` lives in this config because the admin overlay is client-gated; treat the gate as a deterrent, not a security boundary, and rely on RLS for actual data protection.

When changing Supabase RLS or table schema, remember the client uses the anon role — every read/write path must have a matching policy. A recent commit (`76fc0fd`) was specifically about a missing RLS policy surfacing as a bad error message on order status update.

## Architecture

**Two UIs in one document:**
1. Public order form (default view) — customer fills contact info + product quantities, submits an order.
2. Admin overlay (`#adm-ov`, opened via "Správa skladu" → password/TouchID) with tabs: warehouse availability, orders list, delivery notes.

**Product catalog** lives as a hardcoded `const P = [...]` array (~60 items) starting around line 814. Each item has `cat, name, baleni, sklad, trv, voc` (price excl. VAT per pack), `ok` (default availability), `vahy` (priced by weight), `voc_kg`. The catalog is the source of truth for *which products exist*; per-product state is layered on top.

**State layering** (reconstructed by `_applyState()` from a single `product_state` row, id=1):
- `avail[idx]` — current availability toggle
- `prodOverrides[idx]` — per-product edits (price, packaging, stock count, …) merged onto `P[idx]`
- `archived[idx]` / `deleted[idx]` — hide-from-list flags
- `customProds[]` — admin-added products appended to `P` with `_custom: true`
- `stockQty[idx]` — derived stock cap used to clamp quantity inputs

If Supabase fails on load, the same shape is reconstructed from `localStorage` keys (`df_av`, `df_po`, `df_arch`, `df_del`, `df_cp`). When you add a new piece of product state, update **both** the Supabase row shape and the localStorage fallback in the loader at the bottom of the script.

**Supabase tables used:**
- `orders` — customer info, `items` jsonb, `total_without_vat`, `status` (`storno`, `archivovana`, …), `user_id` (nullable for guest orders)
- `delivery_notes` — analogous, with `order_id`, `delivery_date`, `vahy`/`vahy_kg` per item
- `product_state` — single-row (id=1) blob of admin state described above
- Supabase Auth — optional customer login; `_onAuthChange` toggles the "Moje objednávky" UI; guest orders also work

**Code conventions inside `js/app.js`:**
- Vanilla ES5-ish JS, `var`/`function`, no modules. Match the existing style — don't introduce `let`/`const`/arrow functions in a way that breaks the surrounding flow.
- Inline `onclick="..."` handlers in `index.html`; functions defined at top level of `app.js` are global. Renaming a handler means editing both the function and every `onclick=` referencing it.
- IDs are short and reused as DOM keys (`q<idx>` for quantity inputs, `pc` for product container, `sb` summary, etc.).
- Private/internal helpers and globals are prefixed `_` (`_db`, `_user`, `_dlItems`, `_he`, `_applyState`, `_buildDLHtml`).
- Money formatting goes through `fmt(n)` (cs-CZ locale, " Kč" suffix). VAT is always `VAT` (0.12). Don't hardcode the rate.
- HTML interpolation uses string concatenation; user-supplied strings going into HTML must be escaped via `_he()`.

## When editing

- Three files: structure → `index.html`, styles → `css/styles.css`, logic + product catalog → `js/app.js`. Don't fragment further without a real reason; the flat structure is deliberate for static hosting.
- Adding a new secret means: add it to `js/config.example.js`, read it from `_CFG` near the top of `app.js`, and add the corresponding `secrets.*` line in `.github/workflows/deploy.yml`.
- Czech UI strings, date formats (`cs-CZ`), and currency (`Kč`) are part of the product. Don't translate or normalize them.
